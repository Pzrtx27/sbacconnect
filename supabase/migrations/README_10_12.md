## สิ่งที่ต้องแก้เอง หลังรันเสร็จ

### 1. หมวดสินค้าต้องตรงกัน — ไม่งั้นเมนูจะไม่มีตัวเลือกให้เลือกเลย

ไฟล์ 11 ตั้งกลุ่มตัวเลือกกลางไว้ให้ใช้กับหมวดเหล่านี้:

```
coffee, tea, soda, drink, กาแฟ, ชา, โซดา, เครื่องดื่ม, นม
```

คำสั่งตรวจสอบท้ายไฟล์ 11 จะบอกว่าหมวดจริงใน `products` ตรงกันไหม
ถ้าเห็นบรรทัดที่ขึ้นว่า *"ยังไม่มีตัวเลือก"* และหมวดนั้นเป็นเครื่องดื่ม ให้เพิ่มหมวดเข้าไป:

```sql
update public.option_groups
   set applies_to_categories = applies_to_categories || array['ใส่ชื่อหมวดจริงตรงนี้']
 where product_id is null;
```

หมวดที่เป็นขนม/ของกินไม่ต้องเพิ่ม — ตั้งใจให้ไม่มีตัวเลือก "ร้อน/เย็น/ปั่น"

### 2. ราคาตัวเลือก — ต้องไปถามร้านจริง

ราคาที่ใส่ไว้เป็นตัวเลขจากแผน ยังไม่ได้ยืนยันกับร้าน
(หน่วยใน DB เป็น **สตางค์** — 5 บาท = `500`)

| กลุ่ม | ตัวเลือก | ที่ตั้งไว้ |
|---|---|---|
| ประเภท | ร้อน / เย็น / ปั่น | 0 / +5 / +10 บาท |
| ขนาด | ปกติ / พิเศษ | 0 / +10 บาท |
| ระดับความหวาน | ไม่หวาน / น้อย / ปกติ / มาก | 0 ทุกตัว |
| ท็อปปิ้ง | ไข่มุก / วิปครีม / ช็อตเพิ่ม / เจลลี่ | +10 บาท ต่อรายการ |

แก้ราคาทีละตัว:

```sql
update public.options set price_delta_satang = 700 where name = 'ปั่น';
```

### 3. เมนูที่ไม่ควรมีตัวเลือกบางกลุ่ม

เช่นเค้กที่สั่ง "ปั่น" ไม่ได้ — วิธีที่ถูกคือแก้ `applies_to_categories` ตามข้อ 1
ถ้าอยากได้ตัวเลือกเฉพาะของเมนูเดียว ให้สร้างกลุ่มที่ผูกกับเมนูนั้นตรง ๆ:

```sql
insert into public.option_groups (product_id, name, min_select, max_select, sort_order)
values (1, 'ระดับความเข้ม', 1, 1, 50);   -- 1 = id ของเมนูใน products
```

กลุ่มของเมนู **ชนะ** กลุ่มกลางที่ชื่อเดียวกันเสมอ

### 4. รูปเมนู (ไม่บังคับ)

ไฟล์ 11 เพิ่มคอลัมน์ `products.image_url` ไว้แล้ว
อัปโหลดรูปขึ้น Storage แล้วเอา public URL มาใส่ ถ้าไม่ใส่หน้าเว็บจะใช้อีโมจิเดาจากชื่อเมนูเหมือนเดิม

```sql
update public.products set image_url = 'https://.../latte.jpg' where id = 1;
```

### 5. เลิกขายตัวเลือกไหน — อย่าลบ

ลบแล้วออเดอร์เก่าที่อ้างถึงจะพัง ใช้วิธีปิดแทน:

```sql
update public.options set is_active = false where name = 'เจลลี่';
```

## จุดต่อสำหรับงาน QR ของเพื่อน

ส่งสามอย่างนี้ให้เพื่อนพอ ไม่ต้องอธิบายทั้งระบบ

**1. QR เข้ารหัสอะไร**

```
sbac://order/{pickup_code}?t={pickup_token}
```

ทั้งสองค่าอยู่ในผลลัพธ์ที่ `place_order_v2` คืนกลับมาตอนสั่งสำเร็จ

**2. ยืนยันการรับของยังไง**

```js
const { data } = await supabase.rpc('complete_order', {
  p_pickup_code: '0421',
  p_token: 'a3f9...',
});
// data.ok === true  -> ปิดออเดอร์แล้ว
// data.error === 'ALREADY_COMPLETED' -> สแกนซ้ำ
// data.error === 'ORDER_NOT_FOUND'   -> QR ปลอมหรือพิมพ์ผิด
// data.error === 'FORBIDDEN'         -> บัญชีนี้ไม่ใช่เจ้าหน้าที่หน้าร้าน
```

**3. ใครสแกนได้**

เฉพาะบัญชีที่มี role `pos`, `cashier` หรือ `sysadmin` ในตาราง `user_roles`
ฝั่งเพื่อนไม่ต้องเช็คเอง ฟังก์ชันเช็คให้แล้ว

> ทำไมต้องมี `pickup_token` ไม่ใช้ `pickup_code` อย่างเดียว:
> `pickup_code` เป็นเลข 4 หลัก มีแค่ 10,000 ค่า ไล่เดาหมดในไม่กี่วินาที
> `pickup_token` เป็นค่าสุ่ม 128 บิต เดาไม่ได้จริง ๆ

## ตรวจว่าใช้ได้จริง

รันในฐานะบัญชีนักเรียนที่ล็อกอินอยู่ (ผ่านแอป ไม่ใช่ SQL Editor เพราะ SQL Editor ไม่มี JWT):

```js
// 1. เมนูต้องมี option_groups ติดมาด้วย
await supabase.rpc('menu_with_options');

// 2. สั่งจริง — ราคาที่หักต้องรวมส่วนต่างของตัวเลือกแล้ว
await supabase.rpc('place_order_v2', {
  p_items: [{ product_id: 1, qty: 1, option_ids: [2, 5] }],
  p_idem: 'test:' + crypto.randomUUID(),
  p_note: 'ทดสอบ',
});
```

ลองยิงโดยไม่ส่ง `option_ids` ของกลุ่มที่บังคับเลือกดู ต้องได้ `OPTION_RULE_VIOLATED` กลับมา
นั่นคือหลักฐานว่ากติกาตัวเลือกถูกบังคับที่ฝั่งเซิร์ฟเวอร์ ไม่ใช่แค่ที่หน้าเว็บ
